# HMDP-Plus end-to-end seckill benchmark — 2026-09-01

## Conclusion

The reproducible end-to-end result for the current single-machine environment is
**300 business flows/s** (approximately **600 HTTP requests/s**) for 30 seconds.
All **9,001** accepted requests were consumed from Kafka and persisted to the
sharded MySQL tables, with no dropped k6 iterations, no request failures, no
Kafka lag and no rollback failures.

Do not describe the 500-flow/s run as fully successful. Its synchronous entry
path accepted all requests, but the asynchronous consumer could not finish every
message inside the project's 10-second message-age limit.

## Environment and scope

- Host: Apple M5, 10 CPU cores, 16 GB RAM, macOS 26.6.2
- JVM: Java 25, fixed 1 GB heap (`-Xms1g -Xmx1g`)
- MySQL 8.4.11, Redis 8.10.1, Kafka 4.3.1, k6 2.2.0
- Application, k6 and all infrastructure ran on the same host
- Flow: Redis login session -> one-time access token -> Redis Lua atomic stock
  deduction and one-user-one-order check -> Kafka -> sharded MySQL order and
  reconciliation-log persistence
- Each load tier used a dedicated voucher and a unique user per flow
- `RATE` means business flows/s. Every flow sends two HTTP requests.

These figures are suitable for a local benchmark and relative comparison, not a
claim about a distributed production deployment.

## Final measured runs

| Business load | HTTP rate | Duration | Accepted at entry | Persisted orders | Final success | Flow P95 / P99 | Kafka final lag | Result |
|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 300 flows/s | ~600 req/s | 30 s | 9,001 | 9,001 | 100% | 3 ms / 5 ms | 0 | Stable end-to-end |
| 500 flows/s | ~1,000 req/s | 30 s | 15,001 | 12,179 | 81.19% | 4 ms / 9 ms | 0 after timeout handling | Entry stable; consumer over limit |

For the 300-flow/s run, HTTP request latency was P95 **1.55 ms** and P99
**2.65 ms**. k6 recorded 18,002 HTTP requests, 0 HTTP failures and 0 dropped
iterations.

## End-to-end consistency checks

### Stable 300-flow/s run

- Kafka lag: 0 across all four partitions
- MySQL orders: 9,001
- MySQL reconciliation logs: 9,001
- MySQL remaining stock: 499 from an initial 9,500
- Redis remaining stock: 499
- Redis purchased-user cardinality: 9,001
- Redis trace-log cardinality: 9,001
- Rollback failure logs: 0

### 500-flow/s boundary run

- Entry accepted: 15,001/15,001
- MySQL orders and Redis purchased users: 12,179
- Timed-out messages rolled back: 2,822
- MySQL and Redis remaining stock: both 3,821 from an initial 16,000
- Redis trace logs: 17,823 (15,001 deductions + 2,822 restores)
- Rollback failure logs: 0

The boundary run demonstrates that request acceptance/QPS alone is not an
end-to-end success metric. Final persistence, Kafka lag and Redis/MySQL
consistency must be checked together.

## Defect found during stress testing

The original rollback Lua script deleted the whole Redis stock key on the first
timed-out message. This caused later seckill requests and every subsequent
rollback to fail, amplifying Kafka consumer backlog. The script now restores only
the deducted quantity with `INCRBY`. A pre-fix 1,000-flow/s run is intentionally
excluded from capacity conclusions because this defect invalidated its final
state.
